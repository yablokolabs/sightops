## 1. The problem

Someone is standing in front of a machine that is not working. The expertise
needed to understand it is somewhere else.

The original inspiration is not hypothetical. The founder lives about an hour
from his parents. His mother called because their dishwasher had stopped
working. He could not drive over, so he asked her to send photographs of the
control panel, looked at them, asked for another shot at a different angle,
asked her to check specific things, and gradually worked out what was wrong.

That sequence is what SightOps automates:

```
observe → inspect the image → form a hypothesis → identify missing evidence
        → request a better view → inspect the new evidence → recommend an action
```

## 2. What is actually novel here

Plenty of systems can identify an appliance from a photo and generate plausible
text about it. The interesting problem is different, and it is a perception
problem before it is a language problem:

> **A system that does not know whether it has measured something well enough
> will confidently answer anyway.**

SightOps is built around the opposite behaviour. Every measurement carries the
criteria behind its confidence, a gauge reading that fails a geometric validity
check is *withheld* rather than reported, and an agent decides from that
evidence whether to conclude or to ask for a better photograph. The distinguishing
capability is knowing what it has not measured well enough.

This was not a design aspiration that survived contact with reality by
accident — it was forced by a defect. See section 5.

## 3. What was built

A working application: React + TypeScript client, FastAPI backend, OpenCV 5
vision engine, a bounded agent loop with eleven typed tools, SQLite and a
filesystem evidence store, ElevenLabs voice guidance, and an approval gate in
front of every consequential action. Both a household troubleshooting mode and
an industrial inspection mode run on the same vision, agent, storage and
workflow components.

## 4. How OpenCV is used

OpenCV is not a decoder in front of a vision-language model. It is the
measurement instrument, and the model only interprets what it produced.

| Stage | Operations |
|---|---|
| Ingestion | `imdecode` behind a size cap and a pixel cap |
| Preprocessing | `cvtColor`, `resize` (INTER_AREA), `bilateralFilter`, `createCLAHE` on the Lab L channel |
| Rectification | `Canny`, `morphologyEx`, `findContours`, `approxPolyDP`, `getPerspectiveTransform`, `warpPerspective` |
| Gauge | `medianBlur`, `HoughCircles`, 720-angle × 24-sample radial scan, median/MAD normalisation, parabolic peak refinement, shape validation |
| Indicator | `cvtColor(BGR2HSV)`, V/S thresholding relative to the region's own brightness, `morphologyEx`, `findContours`, `contourArea`, 180-bin hue histogram |
| Switch | `cvtColor`, `GaussianBlur`, `threshold(THRESH_OTSU)`, `findContours`, `PCACompute2` |
| Display | percentile-based stroke detection and a bounded lit-fraction test |
| Quality | `Laplacian` variance normalised by the image's own standard deviation; clipping fractions; resolution bounds |
| Change | `absdiff` as context, alongside a structured measurement diff |
| Evidence | `rectangle`, `circle`, `arrowedLine`, `putText`, `imencode` |

## 5. The agentic loop, with a real trace

The demonstration trace, reproduced by `backend/scripts/verify_demo_scenarios.py`
on every run. Every value in it came from OpenCV:

```
OBSERVATION 1   pump panel photographed from an angle, with a reflection
  warning_led_01        RED     confidence 0.97
  pressure_gauge_01     UNKNOWN  (needle shape validation failed — no value published)

DECISION        pressure_gauge_01 is not measured well enough to draw a conclusion
ACTION          request_new_view(target=pressure_gauge_01)
STATE           WAITING_FOR_USER

OBSERVATION 2   same panel, square-on, diffuse light
  pressure_gauge_01     87.16 PSI  HIGH  confidence 0.96   (true 87.0)
  warning_led_01        RED

ACTION          compare_observations  → 2 changes recorded
ACTION          record_diagnosis      → abnormal condition confirmed
ACTION          create_incident       → severity high
ACTION          request_human_approval
STATE           AWAITING_APPROVAL

HUMAN           approves
ACTION          simulated remediation recorded; nothing executed
STATE           COMPLETED
```

The step that matters is the third line. The system had a red warning lamp and
*no* pressure reading, and instead of inferring the pressure from context it
asked for another photograph.

The loop is bounded: 8 steps, 12 tool calls, 2 reinspection rounds, 90 s per
step. The reinspection budget is counted from the persisted trace, so re-running
after a new upload cannot reset it.

### Live reasoning and the deterministic policy

The Nebius model drives the same tool loop in live mode, receiving OpenCV's
measurements as an evidence digest and choosing the next tool. Tool calling was
verified against `Qwen/Qwen3.5-397B-A17B`, `zai-org/GLM-5.3`,
`deepseek-ai/DeepSeek-V4-Pro` and `moonshotai/Kimi-K3`; the configured reasoning
model is `Qwen/Qwen3.5-397B-A17B` and `openbmb/MiniCPM-V-4_5` is served for
multimodal interpretation.

Demo mode replaces the model with `app/agent/policy.py`, a hand-written policy
that reads the same measurements. This is a policy, not a replay: it defers to
each measurement's own `requires_reinspection` flag, and running it on a healthy
panel produces a completely different trace from running it on a faulty one.
Demo mode is labelled in the UI and in every timeline entry it produces, and it
is also the degraded fallback when the model is unavailable — the run continues
and the timeline says why.

## 6. Measured evidence

Full detail, including counterexamples, in `docs/evaluation/results.md`. Produced
by `backend/scripts/evaluate.py`, 136 gauge attempts and 17 controlled
degradations, against exact ground truth (the fixtures *drew* the values):

| Metric | Result |
|---|---|
| OpenCV version | `5.0.0` (`opencv-python==5.0.0.93`), major-version claim verified at runtime |
| Gauge mean absolute error | **0.4724 PSI** (0.47 % of full scale), median 0.19 PSI |
| Gauge p95 / max error | 1.54 PSI / 3.32 PSI |
| Readings published / refused | 112 / 24 |
| **Wrong-value escape rate** | **0.9 %** — 1 reading, listed by name |
| Indicator macro precision / recall | 0.9861 / 0.9853 |
| Display lit-vs-blank | 79.4 % (27/34) |
| Switch position | 100 % (17/17) |
| ROI localisation | 100 % (136/136) |
| Agent task success | 4/4 |
| Active-perception precision / recall | 1.0 / 1.0 |
| Vision analysis latency | mean 22 ms per 1280×720 frame, four regions |
| Backend tests | 165 passing |

The one escaping reading is stated rather than hidden: on the `perspective`
variation a true 43.5 PSI was published as 46.82 at confidence 0.796 — an error
of 3.32 PSI, just over the 3 PSI tolerance. It is in the results table with its
variation, values and confidence.

### The defect that shaped the design

The first gauge implementation reported **28 PSI for a true 87 PSI at
confidence 0.72**. When a frame is rotated or perspective-distorted and the
circle Hough cannot find the dial, the radial scan runs from a displaced centre
and still produces a peak that the original confidence formula rated highly.

The fix was not a threshold tweak. A peak now has to satisfy two independent
geometric tests before a value is published: the sampled ray must be
consistently on the needle's side of the midpoint between the ray and the dial
(`coverage ≥ 0.60`), and the angular peak must be narrow (`FWHM ≤ 14°`). Below
`REPORT_FLOOR = 0.50` confidence no value is published at all and the state
becomes `UNKNOWN`, with the reason written into the measurement's notes and the
raw geometry still returned so the refusal is auditable.

That is where the product's defining behaviour came from: the system learned to
withhold a number, because a reliability tool that prints a wrong pressure is
worse than one that says it could not read the gauge.

## 7. Safety position

SightOps is decision support. It never controls machinery, and there is no code
path that could:

- **Approval is enforced in the data model.** `create_incident` defaults
  `requires_approval` to true, and the industrial trace stops in
  `AWAITING_APPROVAL`. Nothing reaches `COMPLETED` with a remediation recorded
  as approved except the human `/approve` endpoint.
- **Remediation is simulated and labelled as such** in the API response, the
  timeline and the UI, which renders the proposed action inside a panel headed
  `SIMULATED ACTION — REQUIRES APPROVAL`.
- **No actuation surface exists.** `ToolContext` has no control, execute,
  shutdown or actuate member, and `backend/tests/test_safety.py` asserts it.
- **Household guidance stays external.** No instruction to open energised
  equipment, bypass an interlock, modify wiring or disable a protective device.
- **Escalation over guessing.** `UNKNOWN` states, withheld values and
  reinspection requests are first-class outcomes.
- **Untrusted input is validated** (content type, 12 MiB cap, decode, 32 px
  minimum, 40 M pixel cap) before any processing, and tool arguments are
  validated from model output before execution.

## 8. AWS eligibility — stated honestly

**AWS integration is NOT IMPLEMENTED.** No AWS account is used, no resource has
been provisioned, and no AWS component has been benchmarked. The $150 compute
grant was **not awarded**.

Consequences, stated plainly rather than glossed:

- SightOps runs entirely on the existing Azure VM, on CPU, with no GPU. It does
  not require AWS to run or to be evaluated.
- No Graviton instance has been used and COOL has not been installed or
  measured. `docs/benchmarks/cool-methodology.md` is a method with no results.
- The provider interfaces (`EvidenceStorage`, `Repository`, `ModelProvider`,
  `VoiceProvider`) were designed so the S3, DynamoDB and Bedrock adapters
  described in `docs/architecture/aws.md` are additions rather than a rewrite.
  That is a design claim, not an implementation claim.
- Competition eligibility with respect to AWS requirements is subject to the
  organisers' decision.

No performance or cost figure relating to AWS appears anywhere in this
repository, because none has been measured.

## 9. Limitations and future work

Stated so a reader can find the edges:

- **Fixtures are synthetic.** Ground truth is exact because the generator drew
  it, and the 17 controlled degradations exist to claw back the difference — but
  real photographs remain unmeasured, and a real photo carries more texture and
  more segmentation work.
- **Regions are configured per equipment profile**, not discovered. Automatic
  detection finds the panel but not which component is which on an unseen panel.
- **OpenCV does not read digits.** Display interpretation stops at lit/blank;
  the 79.4 % figure reflects that limit under glare, occlusion and wrong
  exposure, and each failure is listed with the measurement that caused it.
- **Tool-failure recovery is not a measured rate.** The paths are covered by
  tests and the loop's repeated-failure guard, but no scripted scenario forces a
  failure, so the metric is reported as `null` with a reason.
- **One wrong reading escaped at 3.32 PSI.** Reducing that needs a better dial
  localisation for oblique views — the shape check catches most of the failure
  mode, not all of it.
- **Next:** digit recognition through the multimodal model with the result
  tagged `inferred`; a real-photograph evaluation set; a learned policy trained
  against the measured confidence signals, since the deterministic policy exists
  precisely to generate that data.

## 10. Reproduction

```bash
# Backend
cd backend
python3 -m venv .venv && . .venv/bin/activate
pip install -e ".[dev]"
pytest -q                                    # 165 tests
python3 scripts/verify_demo_scenarios.py     # the demo trace, re-checked
python3 scripts/evaluate.py --out ../docs/evaluation
python3 scripts/check_providers.py           # reports presence, never values
uvicorn app.main:app --host 127.0.0.1 --port 8000

# Frontend
cd ../frontend && npm install && npm run dev
```

The evaluation harness writes `docs/evaluation/results.json` and renders
`results.md` itself, so the published numbers cannot drift from the measured
ones.
