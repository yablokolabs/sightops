# COOL Benchmark Methodology

> **PLANNED — NOT RUN.** No benchmark has been executed. There are no results in
> this document and none anywhere else in the repository. Running it provisions
> billable AWS EC2 capacity and must not be done without authorisation.

The only measurements that exist today are the local ones produced by
`backend/scripts/evaluate.py` on the existing Azure VM, and they are reported in
`docs/evaluation/results.md`. The methodology below exists so that a future
comparison is reproducible rather than anecdotal.

---

## 1. The question being asked

Two separate questions, and conflating them is the most common way a benchmark
of this kind misleads:

1. **Single-frame latency** — does one 1280×720 analysis complete faster on
   Graviton with COOL than on the x86 baseline? This is what a person waiting
   for a diagnosis experiences.
2. **Throughput per unit cost** — how many analyses per dollar-hour? This is what
   a deployment with concurrent users experiences.

A CPU-bound vision workload can improve on one and not the other, so both are
reported, and neither is extrapolated to the other.

## 2. The workload

Exactly the work the product performs, not a microbenchmark:

- **Input**: the fixtures generated by `app/fixtures/generate_panels.py` at
  1280×720, the same frames the accuracy evaluation uses, so the benchmark and
  the accuracy numbers describe the same pixels.
- **Region configuration**: the shipped `industrial_panel_v1` profile — one
  analog gauge, two indicator lamps, one selector switch. Four regions.
- **Entry point**: `VisionEngine.analyze(frame, image_id=..., profile=...)`, so
  the measurement includes preprocessing and annotation-free analysis exactly as
  the API path does. Calling `cv2` operations directly would measure a program
  that does not exist.

The operations that dominate CPU, and which the benchmark therefore reports
individually as well as in total:

| Operation | Where | Why it dominates |
|---|---|---|
| Gauge radial scan | `gauges._radial_samples` | 720 angles × 24 samples = 17,280 samples per gauge, gathered with numpy fancy indexing |
| `cv2.HoughCircles` | `gauges._dial` | The single most expensive call in the pipeline; a gradient accumulator over the dial ROI |
| Indicator HSV segmentation | `indicators._lamp_blob` | `cvtColor` plus two morphological passes and a contour search, per lamp |
| Laplacian quality scoring | `quality.blur_score` | `cv2.Laplacian` plus variance over the whole frame and per region |
| Panel detection | `regions.detect_panel` | Canny, a morphological close, and contour approximation over the full frame |

Reporting the split matters: if the total improves but `HoughCircles` does not,
the win came from a cheaper operation and would likely also appear on x86 with a
different build.

## 3. The comparison

| Arm | Hardware | OpenCV distribution |
|---|---|---|
| Baseline | x86_64 (the existing Azure VM) | `opencv-python==5.0.0.93` wheel |
| COOL on Graviton | arm64 Graviton | Cloud-Optimized OpenCV Library |
| Optional | x86_64 with AVX-512 | stock wheel, to separate "arm64" from "build flags" |

The third arm is worth the effort. Without it, a difference between arms one and
two cannot be attributed to COOL rather than to the architecture, and the claim
"COOL is faster" would be unsupported.

## 4. The harness

A single script, run identically on every arm, that:

1. Verifies `cv2.__version__` and records it, plus `cv2.getBuildInformation()`
   reduced to the CPU baseline and dispatch flags — the build is the independent
   variable, so it has to be captured.
2. Loads the fixtures from source and hashes the fixture set, so an accidental
   generator change between runs is detectable.
3. Runs **warm-up iterations and discards them**, then N measured repetitions.
   Warm-up matters here because the first `cv2.HoughCircles` call pays lazy
   initialisation that has nothing to do with steady-state throughput.
4. Pins to a fixed thread count. `cv2.setNumThreads(1)` for the single-frame
   latency arm, and a separate run at the default for the throughput arm, since
   OpenCV parallelises internally and the two answers differ.
5. Reports mean, median, p95 and the spread, not a single number. A benchmark
   reporting only a mean of a heavy-tailed latency distribution is not usable
   for capacity planning.
6. Measures CPU seconds consumed (`resource.getrusage`) and peak RSS, so a
   faster arm with worse memory behaviour is visible.

### Command sketch

Not to be run without authorisation — it bills.

```bash
# On each arm, from a clean checkout:
cd backend
python3 scripts/evaluate.py --out /tmp/eval-<arm>          # accuracy + local perf
python3 scripts/bench_cool.py --arm <name> \
    --repetitions 200 --warmup 20 --threads 1 \
    --out /tmp/bench-<arm>.json                            # this benchmark
```

`scripts/bench_cool.py` exists and is runnable. It records everything section 5
lists — the `--arm` label verbatim, OpenCV version and build information, the
fixture-set digest, the git revision, the warm-up count that was discarded, the
latency and throughput distributions, `getrusage` CPU seconds and peak RSS, and a
per-operation split — and it refuses to be mistaken for a cloud result: it prints
an authorisation banner and stores the arm name unchanged.

It has been run **only** as a local smoke test on the development VM
(`--arm x86-baseline`, 12 measured repetitions, 3 discarded warm-ups), which is
what proves the harness works. That is an x86-64 measurement of this machine and
is **not** a COOL, Graviton or AWS result. The arms in section 6 remain unrun
because they require the authorised AWS compute that was never granted; the
smoke output lives outside the repository at `/tmp/bench-smoke.json` and no
number from it is published as a performance claim.

## 5. What must be recorded

A result without this list is not reproducible and should not be published:

- Instance type, vCPU count, architecture (`uname -m`), and the region
- Operating system image and kernel
- OpenCV version **and build flags**
- NumPy version and whether it is a BLAS-linked build, since some `cv2` paths
  route through NumPy
- `cv2.getNumThreads()` at the moment of measurement
- SHA-256 of the fixture set, and the generator commit
- Repetition count and warm-up count
- Mean, median, p95 and spread of single-frame latency
- Throughput at the default thread count
- CPU seconds and percentage of one core, plus peak RSS
- Cost assumption stated explicitly as an assumption, with its date and source

## 6. Honest caveats

- **A CPU-bound vision workload benefits less than a headline number suggests.**
  The pipeline is dominated by `HoughCircles` and a numpy gather loop; neither is
  a simple SIMD-friendly inner product, and both are affected by memory access
  patterns as much as by arithmetic throughput. A wall-clock improvement is a
  real result; an improvement on a synthetic arithmetic kernel would not be
  evidence about this workload.
- **Preprocessing will not be reworked to suit a benchmark.** If COOL is faster
  on the current code, that is the finding. Changing the algorithm to flatter a
  particular library and then calling it a portability win would be dishonest.
- **Single-frame latency and total throughput are different questions** and can
  point in opposite directions once OpenCV's internal threading is involved.
- **Container and cold-start overhead is excluded** from the per-frame numbers
  and reported separately if measured at all, because it belongs to a deployment
  question rather than to the vision pipeline.
- **These numbers would not transfer to real photographs.** The fixtures are
  synthetic; a real photo has more texture, and more of the time would land in
  segmentation and contour work.
- **The only measurements that exist today are local.** If a COOL comparison is
  never authorised, this document stays a method with no results, and no
  performance claim will be made about COOL or Graviton anywhere in this
  repository.
